# Product Truth Passport — frontend

Buyer, Operator and Phase-2 Reviewer UI. Requires Node 24 and npm; exact dependency versions are in package.json and package-lock.json.

From this directory, use `npm.cmd ci`, `npm.cmd test` and `npm.cmd run build` on Windows. The human starts the repository's **frontend** Action. Open [the buyer preview](http://localhost:5173/buyer/DEMO-PROD-01).

Development defaults to `VITE_USE_MOCK=1` through .env.development. For a real backend, set `VITE_USE_MOCK=0` in the process environment or .env.development.local and restart the Action. Requests remain under `/api`, proxied by Vite to `http://localhost:8000`. The production build defaults to the real API; a preview build can be created with `$env:VITE_USE_MOCK='1'` before `npm.cmd run build`.

Routes: `/` operator, `/buyer/:productId` buyer, `/reviewer`, `/observe`, `/orders/:orderId`. Role selection is stored in localStorage and sent as `X-Demo-Role` and `X-Demo-Actor`; backend authorization remains authoritative. Product selection opens the chosen buyer route. An unknown product shows an error. The operator catalog is only requested with the Operator role.

The buyer shows five independent fields, checked times and available origin/mode badges. Passport polling runs every 2 seconds while stale or updating, otherwise every 10 seconds, and pauses in hidden tabs. Evidence opens the full stored passages with the exact excerpt highlighted, allowing whitespace/NFC differences. Within-source passages share a source heading and appear side by side on desktop. Buyer evidence omits PRIVATE text and shows only its count. A changed label pulses the row, yellow for Stale; reduced-motion preferences disable animation. Only the ingredient row shows a server-supplied neutral claim count. Why, receipt and observability work remain for later phases.

Operator v1 provides event buttons, outcome/reason/stale-field messages, counters, runs and trace steps, and a reset confirmation. API errors show route and HTTP status. The mock has an explicit interactive scenario transport; its counters and runs last only for the current page session and reset on a full reload. It is a UI simulation, not pipeline execution. Product copy, passages and authored outcomes stay under src/mock; no PRIVATE source text is bundled.

`npm.cmd run types` exports the checked-out backend's `/openapi.json` through FastAPI TestClient and regenerates src/api/schema.d.ts using pinned openapi-typescript. Phase 2 consumes the sixteen paths from merged contract-2 (2811f3b). It requires backend/.venv with P4's requirements; it starts no server and does not enter the application's startup lifespan. Wire DTOs consume that schema; `PassportView` keeps pending display rows separate. Product presentation and passport metadata may be null. The composite S1 mock is projected to the exact PassportResponse before transport. Contract tests validate S1 mock responses against P1's Pydantic DTOs; tests/test_s2_contract.py validates six S2 request/response payloads against the merged models.

At sync-1 (be91b3b), S1 routes are implemented and the shared fallback gate passed. Use VITE_USE_MOCK=0 to inspect that backend. At contract-2 the four S2 routes expose schemas/ACLs and return 501 pending Stage B; api/reviewTypes.ts aliases generated DTOs plus a joined UI view. S2 mock and intercepted API tests prove frontend behavior, not backend review/publication or the M2 story. There is no automatic mock fallback after an API failure. API keys belong only in backend/.env, never in a VITE variable or frontend file.

Reviewer role opens `/reviewer`: select a task, compare cited passages (seller quotations are labelled), inspect the current finding and result history, and approve/override/reject with a required reason. The client joins flat queue items to history by exact result_id. Because history lacks product_id, full evidence is loaded only when a product's evidence response contains every exact stored citation (passage ID, source kind/version, locator and excerpt); unrelated passages are discarded. Optional lookup failures keep history-backed tasks available, surface a per-task error and retain stored excerpts; probes continue to other products. Cancellation and authorization failures still propagate. Otherwise the UI explicitly shows cited excerpts and a full-passage-unavailable notice. Seller attribution remains “Not supplied” because P1's checkpoint omits it; this is an open CCR. The opened `(result_id, case_revision)` stays pinned even when the queue polls. During submission queue controls are disabled; an API-client lock keyed by case/result/revision also prevents a second in-flight POST across form/workspace remounts. The lock releases after success or failure. A 409 blocks submission until explicit reload; 422 shows the bounded server reason code. Success is confirmed through the history decisions list, not a fabricated local decision. Claim findings use the same workflow. Override fields/citations remain subject to backend validation.

Operator includes a scenario Next button, catalog captions and an adjacent stored Passport polled every 2 seconds. It uses the same product-metadata adapter as the buyer page, preserving supplied mode badges and hidden citation counts. `src/scenarioConfig.ts` lets P4 specify catalog event names; empty configuration uses numeric catalog-name order for the selected product. Errors leave Next at the same step, reset returns it to the start. Run chips include PARTIAL/FAILED and stop_reason; “marked stale — no model call” requires a recorded stale:mark step and zero run model calls. The live preview remains plain language; detailed run data stays in the trace panel.

Seller role on the buyer route reveals a small JSON evidence form. Enter the case reference and an object with idempotency_key, field_keys and content. P1 supports TEXT content ({kind: "TEXT", text}) or encoded IMAGE content ({kind: "IMAGE", media_type, data_base64}); the server validates access and payload. The form displays AdmitResult outcome/reason. REJECTED is an alert; NOOP/DUPLICATE do not imply new processing; ADMITTED confirms submission and says processing was queued only when a job ID is supplied. A response without an admission outcome is an error. No case ID is guessed from a product ID. JSON upload is implemented; a binary image picker and the optional time-travel slider are deferred. This does not add a gate. The additional Phase-2 mock under src/mock/reviewTransport.ts has browser-session-only decisions/history and synthetic lifecycle states; it is separate from the strict S1 mock projection and does not establish policy behavior or create a pipeline recording.

Tests use Node's runner and offline Playwright route interception. They create no listening server or model call. Existing label, transport, guard and lifecycle assertions remain intact; Phase 1 adds evidence, dynamic polling, events, reset, error recovery and read-only buyer checks. The API browser suite checks three full buyer reloads, null presentation, stale/running/failed states, late evidence responses, 501 retry and event double-click protection. S2 adds exact revision submissions, durable-history reads, 409 reload, 422 correction, distinct excerpts from one passage, and adjacent-Passport FALLBACK/REPLAY metadata. These intercepted tests do not establish implemented backend review, image processing or shared replay coverage. The wording scan reads the canonical pattern from backend/tests/test_guards.py.
